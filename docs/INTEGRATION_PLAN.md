# Integration & containerisation plan

Status: **agreed, not started** · 2026-09-25

Goal: connect both sites to the real backend. Customers get **live quotes and counter-offers
from the model** when they submit a booking, and the operator site shows **every booking in real
time**. Remove every mock-data fallback, and run the whole stack locally as three containers
(UI · API · database) with one `docker compose up`.

---

## 1. Current state

| Piece | Talks to backend? | Mock data today |
|---|---|---|
| `drafts/cargo-ship` — operator site (Vessel / Stowage / Statistics / Model) | **No** | 100% — procedural cargo, hard-coded profit, `pages/statsData.js`, `pages/engine.js` |
| `customers/` — customer site (dashboard + intake-a…d) | Yes — `/ports`, `/orders` | Embedded `FALLBACK` port list + localStorage order cache when the API is down |
| `src/` — Next.js app | Yes — episodes, WebSocket, deals | `src/lib/data.ts` drives `VesselPlan`, `Sidebar`, `MoneyHUD` … |
| `backend/` — FastAPI | — | `orders` seeded from a hard-coded `_SEED` list; SQLite only; episodes/deals in memory |

Docs drift: `api.md` says port 8399, `server/app.py` says 8000; `/orders` is undocumented.

## 2. Decisions

| # | Decision |
|---|---|
| D1 | **Retire the Next.js app** (`src/`). Keep the two static sites. |
| D2 | **Keep** the backend's market-rate calibration (Drewry / SCFI anchors). "No market data" = no *mock* data. |
| D3 | Operator screens follow the **current live episode**, with a picker for finished runs. |
| D4 | **Customer bookings are in scope**: priced by the live simulator, with counter-offers and the model's recommendation (§6). |
| D7 | API schema may change freely to suit the UI; prefer the straightforward option. |
| D8 | Operator site is **real-time view** of all bookings; manual operator override is out of scope for now. |
| D5 | **No mock fallbacks anywhere.** API down → explicit error / empty state. |
| D6 | Synthetic data is **local-only**: opt-in via gitignored `.env`, generated by running the real simulator. |

## 3. Target architecture

```
ui   nginx          :8080   /              → operator site (drafts/cargo-ship)
                            /customers/    → customer site
                            /api/*         → api:8000  (incl. WebSocket upgrade for …/stream)
api  FastAPI        :8000   single uvicorn worker (episodes run on in-memory threads)
                            CPU-only torch · runs `alembic upgrade head` on start
db   Postgres 16            named volume · healthcheck · api waits for healthy
```

- **Same-origin `/api`** replaces every hard-coded `http://localhost:8399`, which removes CORS
  and port guessing.
- **Migrations:** Alembic with hand-written revisions (no autogenerate), each with a working
  `downgrade()`, and idempotent on re-run.
  - `0001_orders`: orders table (moved off SQLite)
  - `0002_episodes_events_deals`: persisted episodes, event mirror, deals
- **Ledger:** the hash-chained JSONL files stay the tamper-evident source of truth; Postgres
  mirrors events for querying.
- **Seed:** a `seed` command runs a few seeded simulator episodes plus orders. It only runs when
  `DOCK_SEED=1` is set in the gitignored `.env`, and it lives only in the local Docker volume.
  Anyone who pulls gets an empty, migrated DB.

## 4. Bottlenecks

1. **The operator UI's data doesn't exist in the backend yet.**
   - *Model page* needs obs (112), mask (44), π, V(s), logits and attributions per decision. The
     backend emits only the outcome. → add a `policy.decision` event from `_drive_ppo` (read
     probabilities/value from `model.policy`, gradient×input attribution). The shapes already
     match (`OBS_DIM = 112`, `N_ACTIONS = 44`).
   - *Vessel / Stowage* use ISO bay-row-tier with individual boxes. The backend stowage is bays ×
     stack height (`Slot`: board/discharge call, weight, cargo type). → add a
     `/episodes/{id}/vessels/{vid}/stowage` endpoint with a deterministic bay-row-tier mapper;
     the solver itself is unchanged.
   - *Statistics* is mostly covered by `/compare/*` + live metrics + `/orders`. The UI needs
     adapting to those shapes.
2. **Postgres migration** of orders + persistence of episodes/events/deals (in memory today).
3. **Image size:** torch + stable-baselines3 + py-evm. The CPU-only torch wheel keeps the
   image at ~1 GB instead of 3+ GB.
4. **Single process:** in-memory episode threads, so exactly one API worker.
5. **Precomputed compare artifacts** live in `public/demo/` (a Next.js folder) and need to move
   under `backend/` when Next.js is removed.

## 5. Execution order

1. Retire Next.js: remove `src/`, the Node toolchain files, and relocate `public/demo/*.json`.
2. Docker Compose (ui / api / db) + Alembic; `orders` off SQLite; `_SEED` removed.
   ✔ `docker compose up`, `/health`, orders round-trip.
3. Persist episodes / events / deals; local-only seed.
4. nginx same-origin `/api`; strip customer-site fallbacks (`FALLBACK`, localStorage caches).
5. Live episode + customer bookings (§6): always-on episode, quote/accept/decline endpoints,
   `offers` table, `order.*` events.
6. Customer site: booking form shows the offer menu + recommendation; accept/decline;
   dashboard reads real orders/statuses.
7. Backend additions for the operator UI: `policy.decision` event, stowage endpoint.
8. Wire operator screens (live bookings feed → Stowage → Vessel → Statistics → Model) to
   `/live`; delete `statsData.js` / `engine.js` mocks.
9. Refresh `api.md`, `plan.md` and the `docs/` pages; run end-to-end locally
   (customer books → operator sees it live → deal settles).

## 6. Customer bookings: quote → counter-offer → accept

The simulator already separates pricing (`sim.quote()`), feasibility (`sim.feasible()`) and
commit (`sim._book()`). Only `_customer_accepts()` is simulated (hidden WTP dice); for a real
customer the human's click replaces it.

1. **Always-on live episode.** At API start, run one live episode (PPO, baseline, slow
   real-time pace) and restart it when the horizon ends. A lock serialises the episode thread
   with quote/accept calls.
2. **`POST /orders`** builds a `BookingRequest` in the live sim, generates its options (incl.
   alt hub), and returns synchronously:
   `{order, offers: [{id, kind, vessel, board_day, eta, price_per_teu, total, discount}],
   recommended_offer_id, recommendation: {action, prob}}`.
   Offers are accept / flex-window / alt-hub / split, priced by the bid-price engine and
   filtered by the stowage mask. The recommendation is PPO's pick for this request (obs + mask
   built for it).
3. **`POST /orders/{id}/accept {offer_id}`** re-checks feasibility, then `_book()`s. Counters
   register a settlement deal as today. A stale offer returns `409 offer no longer available`.
   **`POST /orders/{id}/decline`** records the decline.
4. **Events:** `order.created`, `order.quoted`, `order.accepted`, `order.declined` join the
   live stream; customer bookings carry `source: "customer"` on `booking.decision` /
   `cargo.booked`.
5. **Schema:** `orders` gains `status` (`quoted → accepted | declined | expired`, then voyage
   statuses), `episode_id`, `request_id`, `deal_id`; new `offers` table.
6. **Live endpoints:** `GET /live` (current episode snapshot), `WS /live/stream`.
   Sim day ↔ calendar date: day 0 = the episode's start date, shown as dates in the UI.
